# Fast continuation pressure cases

Use these behavioral probes for [Fast outcome continuation](fast-path.md#outcome-continuation-and-completion). A prose claim of ownership is insufficient: identify the next execution action and responsible actor. These cases create no permission or artifact gate.

The reported failure is the baseline: a startup audit finishes with the position repeat's persistence and cause unknown; nobody is diagnosing it, while the coordinator says the retained Fast owner still owns it and promises to route RCA. The audit boundary left the requested outcome unresolved.

| Scenario and pressure | Required behavior | Failure to reject |
| --- | --- | --- |
| Audit complete; cause remains unknown; the bounded assignment has ended. | Fast sends progress and continues the next authorized diagnostic action. If already idle, the current task owner actually calls `followup_task` on that retained identity. | Final handoff, an idle owner label, or a promise to route RCA later. |
| Main has not published a design winner; Fast has useful authorized feature work. | Fast implements and verifies while main explores and reviews concurrently, preserving existing decisions and actual write conflicts. | Waiting for main Step 1/2 merely because the normal path has not selected a design. |
| A feature scaffold exists; requested behavior is still missing. | Fast reports scaffold progress and continues implementing and checking the requested behavior. | Treating the scaffold milestone as the delivered feature. |
| A configuration edit is written; required validation remains. | Fast completes the applicable validation, then commits its verified scoped change. | Stopping at the edit or claiming completion without required evidence. |
| A helper completes one part; another required part remains. | Fast integrates the helper's evidence, commits the completed verified owned change, and advances the remaining work itself or through bounded helpers. | Treating helper completion as Fast completion or transferring accountability to the helper. |
| A repository change passes checks; the scoped commit is still missing. | Fast checks the exact staged scope and makes its own checkpoint commit, then reports the commit and evidence. | Asking main to make the producer commit or reporting completion before it exists. |
| Commit gate rejects the authorized producer commit. | Fast reports the exact effect and bounded route, retains unfinished ownership, and continues safe work while the responsible owner repairs the dependency. | Bypassing the gate, claiming the commit succeeded, or ending as if the requested outcome were complete. |
| Main owns an overlapping write; other authorized work remains ready. | Yield the conflicting writes, name the resume condition, and continue the unaffected work. Serialize only the shared index/target operations. | Parking the entire outcome, forcing stale edits, or declaring completion. |
| A required device or capacity slot is unavailable; no useful independent action remains. | Report the concrete dependency, responsible owner, and resume action; remain accountable and resume when it clears. | Invented activity, false completion, or treating main review alone as the missing resource. |
| Main wants a review helper but capacity is exhausted; Fast has ready work. | Queue the capacity-dependent review action and continue Fast's ready work under its retained owner. | Suspending all Fast execution merely to free capacity for main process or review. |
| Task ownership changes while an incomplete Fast report is being transferred. | Preserve held-report and publication rules; the effective owner processes the remaining action once and preserves the Fast identity. | Dispatch from an obsolete owner or duplicate work assignments. |
| The original provisional result is evidenced, producer checks pass, scoped commits exist, Fast helpers and their tools are finished; main-path work and acceptance remain active. | Fast delivers its complete evidence and becomes idle while main-path writers continue and the mandatory post-Fast sequence advances. | Stopping main-path writers for Fast completion, requiring Fast to repeat solved work, or claiming final acceptance from its checkpoint. |
| The user requested analysis only; the complete requested evidence requires no file changes. | Finish with the analysis evidence and ordinary post-Fast handoff. | Inventing a repair or empty commit to satisfy the completion rule. |
| Late normal-path evidence disproves a required result; Fast is idle after a done claim; closure is imminent. | The current Job owner reopens provisional completion and immediately calls `followup_task` on the retained identity with evidence, unmet criterion, and next bounded action. After renewed genuine completion, restart post-Fast from fresh Step 1, even without new writes. | Relying on the old done claim, promising later routing, messaging an idle Worker, or skipping restart because no files changed. |
| That evidence arrives while Fast already has an active bounded assignment; main owns overlapping writes. | Send the evidence, unmet criterion, and bounded action with `send_message`; preserve the active assignment, yield overlapping writes, and continue independent ready work. | Duplicate dispatch, parking independent work, or forcing conflicting writes. |
| A late finding concerns an unrelated outcome and disproves no required result. | Preserve scope; report it as a post-ECI follow-up without reopening Fast completion. | Expanding authorization or restarting completed work for the unrelated finding. |
| The user explicitly cancels the task. | Stop the task-owned writers and preserve evidence through normal cancellation closure. | Continuing cancelled work or labeling cancellation a clean pass. |
